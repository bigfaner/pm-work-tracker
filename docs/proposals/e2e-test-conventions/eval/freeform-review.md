# Freeform Expert Review

## Background Assessment

This proposal tackles two intertwined problems in the project's test infrastructure. First, the existing conventions documentation under `docs/conventions/testing/` was auto-generated by forge and describes idealized strategies rather than rules extracted from actual code. Second, all end-to-end tests — API, Web, and CLI — are lumped together under `tests/e2e/`, violating the Forge surface model's principle that each surface should have an independent build/dev/test lifecycle. The evidence table in the proposal is compelling: it maps eight dimensions where the framework documentation diverges from actual code patterns, from three different HTTP client approaches coexisting to hardcoded `waitForTimeout(2000)` calls scattered through test files.

The core technical approach is a two-part intervention: first, reorganize the test directory by surface (api/, web/, cli/, shared/) and migrate API tests from Playwright to Vitest; second, codify practical conventions extracted from the real codebase into the existing conventions documents. The proposal claims the Playwright-to-Vitest migration is largely mechanical — changing imports and adjusting one API difference (`test.describe.serial` to `describe.sequential`). It envisions convention rules (E-100 through E-123) that are specific enough to include correct/incorrect code examples and that an AI agent can follow when generating new test scripts.

The proposal rests on several assumptions: that Vitest's `test`/`expect` API is close enough to Playwright's that migration is straightforward, that the `curl()` helper already works independently of Playwright, that the ~49 test files can be migrated in 2-3 hours, and that conventions written after migration will stay in sync with the code. These assumptions deserve scrutiny, which I address below.

## Key Risks

The proposal's most dangerous claim is that the API test migration is mechanical. The assertion "API 测试文件基本只需改 import 和文件名后缀" appears in the migration table and again in the Feasibility Assessment section. This understates the real surface area of a framework migration. Playwright's `test.describe.serial` does not simply become Vitest's `describe.sequential` — Playwright's serial mode guarantees that tests run sequentially and that if one test fails, subsequent tests in the group are skipped. Vitest's `test.sequential` modifier only affects execution order within a concurrent run; it does not propagate failure to skip downstream tests. This is a behavioral difference that will silently change test semantics if not handled explicitly.

风险：Framework API parity claim masks behavioral incompatibility in serial test execution
> "API 测试文件基本只需改 import 和文件名后缀（`-api` 前缀去掉），`curl()` 和 helpers 不变" — If any API test file uses `test.describe.serial` with the expectation that later tests are skipped when an earlier test fails (e.g., a multi-step creation flow where step 2 should not run if step 1 failed), the migration to Vitest will silently change this behavior. Tests that previously short-circuited on failure will now run to completion, potentially producing misleading error output or triggering cascading cleanup failures. The proposal mentions the `.serial` difference only in passing as a footnote in the Constraints section, not as a migration action item.

The proposal defines a `tests/shared/` directory for cross-surface helpers but does not specify the boundary between what belongs in shared versus what is surface-specific. The current helpers.ts file presumably contains a mix — `curl()` is clearly API-only in nature, while `getApiToken()` might be shared across API and Web surfaces, and `login(page)` is clearly Web-only since it takes a Playwright Page object. The proposal does not explain how these concerns will be separated.

问题：Shared helpers boundary is undefined, risking surface-specific leakage
> "共享 helpers 提取到 `tests/shared/`" — The proposal says helpers will be "extracted" to shared/ but does not define criteria for what belongs there versus what stays in a surface-specific location. The helpers specification (E-120 through E-123) mixes concerns: E-120 (config), E-121 (token caching), and E-122 (CLI execution) are genuinely shared, but E-123 (`screenshot(page, tcId)`) is purely a Playwright/Web concept. Placing a function that accepts a Playwright `Page` object in a shared directory that API tests (running Vitest, no Playwright) also import from creates a confusing dependency. If API tests import from shared/helpers.ts and that file imports Playwright types, API tests gain a transitive Playwright dependency — exactly the problem the migration is supposed to eliminate.

The timeline estimate of 2-3 hours for migrating ~49 test files is optimistic even for a purely mechanical change. But the migration is not purely mechanical. Each file needs to be inspected for Playwright-specific patterns that do not have direct Vitest equivalents: custom fixtures injected via Playwright's fixture system, `test.use()` configurations, `page` or `request` parameters in test functions, and Playwright-specific `expect` matchers (e.g., `expect(...).toBeOK()` for API responses, or Playwright's `expect` soft assertion mode). The proposal does not acknowledge these potential patterns at all.

风险：Migration timeline assumes no Playwright fixture or custom test function patterns exist in API tests
> "目录重组 + API 框架迁移：约 2-3 小时（~49 个测试文件的路径和 import 调整）" — The estimate treats each file as requiring only path and import adjustments. If any API test file uses Playwright's fixture injection (e.g., `test('my test', async ({ request, page }) => { ... })`) or custom fixtures defined in `playwright.config.ts`, those patterns have no Vitest equivalent and require structural rewriting. The proposal does not include a preliminary audit step to identify such patterns before committing to the timeline.

The proposal explicitly scopes out CI pipeline adjustments and modifying the Forge configuration. However, splitting tests into separate directories with separate configs and separate package.json files necessarily changes how CI discovers and runs tests. If CI currently runs `npx playwright test` from the project root, that command will no longer find API tests after they move to `tests/api/` with a `vitest.config.ts`. The proposal's Scope section says CI adaptation is "out of scope" but does not acknowledge that the migration will immediately break CI until that adaptation happens.

风险：CI will break immediately upon migration with no transition plan
> "CI pipeline 调整（目录变更后的 CI 适配另议）" — Marking CI adaptation as out of scope creates a window where the migration is partially complete and CI is red. Without a transition plan (e.g., temporary symlinks, or a phased migration where both old and new paths run temporarily), the migration cannot be landed safely on the main branch.

The convention rules (E-100 through E-106 for API, E-110 through E-115 for Web) are well-specified with correct/incorrect examples, which is a genuine strength. However, the anti-pattern lists for both surfaces are surprisingly short and may not cover the full range of patterns visible in the codebase. The evidence table identifies six problematic dimensions, but the anti-pattern lists capture only a subset of what the evidence reveals.

问题：Anti-pattern catalog does not fully cover patterns identified in the evidence table
> The evidence table shows "4 种登录方式（localStorage 注入/表单/API token/cache）" but the Web anti-pattern list only addresses form login redundancy (item 3) and does not mention the API token or cache-based login variants. Similarly, the evidence notes "无 afterAll 清理，数据累积" as a data isolation problem, but neither the API nor Web convention rules include a rule about test data cleanup in `afterAll`/`afterEach`. This gap means the conventions will not prevent one of the documented problems from recurring.

The proposal's "migrate first, then codify" ordering is sound in principle, but it lacks a mechanism to ensure the conventions stay accurate after they are written. The Key Risks table acknowledges "spec drift" as a medium-likelihood, medium-impact risk, but the mitigation — "先完成迁移，再从最终代码提炼规范" — only addresses the initial writing. There is no ongoing mechanism proposed.

风险：No mechanism to prevent spec drift after initial codification
> "先完成迁移，再从最终代码提炼规范" — This mitigation only ensures the conventions are accurate at the moment they are written. Once developers start writing new tests or modifying existing ones, the conventions can drift from practice with no detection mechanism. The proposal does not propose a lint rule, a CI check, or even a periodic review cadence to catch drift.

Finally, the proposal does not address what happens during the migration itself — the transitional state where some files have moved and others have not. With ~49 test files being reorganized, it is likely that the migration will span multiple commits. During that window, relative import paths between test files and helpers will be broken for the partially-migrated set.

问题：No transition state plan for incremental migration
> The proposal implies the migration happens atomically ("逐个 surface 迁移并验证") but does not define what "逐个 surface" means in terms of commit boundaries, branch strategy, or how shared helpers are handled when some consumers have moved and others have not. If helpers.ts is moved from `tests/e2e/` to `tests/shared/` in the first commit, all unmigrated files break. If helpers stays in the old location until all files migrate, the new surface directories have awkward relative paths (`../../e2e/helpers.js`).

## Improvement Suggestions

The most critical gap is the framework API parity assumption. The proposal needs an explicit migration compatibility matrix.

建议：Add a Playwright-to-Vitest API compatibility matrix to the migration section
Addresses: Framework API parity risk
> What changes: Before the migration begins, add a table to the proposal mapping every Playwright test API used in the API test files to its Vitest equivalent. Specifically cover: `test.describe.serial` (note the behavioral difference in failure propagation), `test.skip`/`test.only` (semantics differ around concurrent execution), `test.use()` (no Vitest equivalent — needs a different approach), custom fixtures defined in playwright.config.ts (need to become Vitest beforeEach or module-level setup), and any Playwright-specific `expect` matchers. This matrix should be produced by auditing the actual API test files, not by assumption. Include this audit as a required step before the migration timeline is committed.

The shared helpers boundary needs explicit definition to prevent surface-specific dependencies from leaking.

建议：Define shared/helpers.ts ownership rules and split surface-specific helpers
Addresses: Shared helpers boundary problem
> What changes: Add a rule to the helpers specification (or as a new E-1XX convention) stating that shared/helpers.ts must not import from any test framework or surface-specific library. Surface-specific helpers (like `screenshot(page, tcId)` which requires Playwright, or `login(page)` which requires a Page object) should live in their respective surface directories (e.g., `tests/web/helpers.ts`). Only genuinely framework-agnostic utilities (config loading, token caching, CLI execution, the `curl()` HTTP wrapper) belong in `tests/shared/`. This makes the boundary enforceable by a simple import check: if shared/helpers.ts imports `@playwright/test`, it is violating the convention.

The CI transition needs to be addressed even if the full CI redesign is deferred.

建议：Include a CI transition plan as a required part of migration scope
Addresses: CI breakage risk
> What changes: Either promote CI adaptation to in-scope with a concrete plan (e.g., after moving API tests to tests/api/, add a new CI step `cd tests/api && npx vitest run` alongside the existing Playwright command), or define a phased migration strategy where a compatibility layer (e.g., a test runner script that discovers tests in both old and new locations) bridges the transition. The current "out of scope" stance is only viable if the entire migration lands in a single commit on a branch and is validated before merge — but the proposal also says "逐个 surface 迁移", which implies incremental commits.

The anti-pattern catalog needs to cover the full range of evidence-documented problems.

建议：Expand anti-pattern lists to cover all evidence table findings
Addresses: Incomplete anti-pattern coverage
> What changes: Add to the API anti-pattern list: (1) missing test data cleanup in afterAll/afterEach, (2) mixed assertion styles (toBe vs toBeTruthy for status codes), and (3) token management outside of getApiToken(). Add to the Web anti-pattern list: (1) cache-based or direct API token authentication when login(page) is available, and (2) missing test data cleanup. Each of these is directly evidenced by the proposal's own evidence table but absent from the anti-pattern catalogs. This ensures the conventions prevent all documented problems, not just a subset.

The proposal needs a plan for the incremental migration transition state.

建议：Define a migration order that maintains a working test suite at every commit
Addresses: No transition state plan
> What changes: Specify that the migration proceeds surface by surface in this order: (1) Create `tests/shared/` and add a re-export file at `tests/e2e/helpers.ts` that re-exports from `tests/shared/helpers.ts` — this preserves backward compatibility. (2) Migrate CLI tests (smallest surface, no framework change). (3) Migrate API tests to `tests/api/` with Vitest. (4) Migrate Web tests to `tests/web/`. (5) Remove the old `tests/e2e/` directory and the re-export shim. Each step should be a separate commit where all tests pass. This is a well-known pattern for directory restructuring migrations and avoids any window where the test suite is broken.

Finally, the spec drift problem needs a lightweight prevention mechanism, not just a one-time mitigation.

建议：Add a spec drift detection mechanism to the conventions maintenance plan
Addresses: Spec drift risk
> What changes: Include in the conventions documents a "Last Validated Against" date and commit hash. When the proposal says it will codify conventions from the migrated code, it should also specify a recurring validation: either a manual quarterly review, or better, an automated check that counts how many test files deviate from the conventions (e.g., how many API test files import something other than vitest, or how many use `waitForTimeout`). This does not need to be a full linter — even a simple grep-based check in CI that fails if forbidden patterns appear would prevent the most damaging drift.
