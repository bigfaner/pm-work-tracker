## Contract: step-1-delete-main-item-cascade (885/1000 — PASS)

### Completeness: 175/200

**Coverage**: All journey outcomes for Step 1 are covered: success (happy path Step 1), cancelled (edge case E1), unauthorized (E4), session-expired (E8), not-found (E6). The "success" outcome correctly covers the cascading sub-item deletion.

**Deductions**:

- (-10) No Fact Table section. Contracts reference facts (e.g., "prd-spec Story 3 AC1") but there is no explicit fact table listing the source facts and their traceability. The `<!-- reasoning: -->` comments partially compensate, but a structured fact table is the rubric standard.

### Semantic Purity: 185/200

**Natural language**: All outcomes use plain English. Preconditions, inputs, outputs, and state descriptions are domain-level and readable by product stakeholders.

**Deductions**:
- (-10) Outcome "success" State field references `deleted_flag set` — this is an implementation detail leaking into the contract. Should say "item is marked as deleted (soft-delete)" or similar.
- (-5) Outcome "not-found" references `ITEM_NOT_FOUND` error code which is implementation-specific. Should describe the semantic meaning ("item does not exist").

### Precondition Exclusivity: 140/150

**Distinctness**: Each outcome has sufficiently distinct preconditions. "success" requires a main item with 3 sub-items + PM permission; "cancelled" requires the dialog to be open; "unauthorized" requires missing permission; "session-expired" requires expired session; "not-found" requires non-existent ID.

**Deductions**:
- (-10) Outcome "cancelled" preconditions overlap with "success" — both assume a main item with sub-items exists. The distinguishing factor (dialog is open vs. user clicks delete) is in the Input, not the Precondition. The precondition should explicitly state the user has already initiated the delete action and the confirmation dialog is displayed.
- (-0) Preconditions are sufficient for each outcome — no missing conditions.

### Fact Alignment: 120/150

**Traceability**: The contract references facts from the journey (e.g., prd-spec Story 3). Inferred outcomes are correctly annotated with `<!-- source: inferred -->` and `<!-- reasoning: -->` comments.

**Deductions**:
- (-20) No structured Fact Table. While reasoning comments exist for inferred outcomes, there is no formal mapping of claims to source facts. The journey uses `<!-- fact: -->` annotations but the contracts do not carry these forward in a structured way.
- (-10) The "cancelled" outcome has no source annotation at all (neither fact reference nor inferred marker). It corresponds to journey E1 but this traceability is missing.

### Surface Fitness: 130/150

**Surface tags**: The journey defines `surface_types: ["web", "api"]`. The contract's outcomes mix web and API surfaces. Step 1 in the journey is tagged `<!-- surface: web -->`.

**Deductions**:
- (-10) Outcomes lack individual surface tags. "unauthorized" and "not-found" are API-surface outcomes, while "success", "cancelled", and "session-expired" are web-surface. Without per-outcome surface tags, test generators cannot correctly assign test types.
- (-10) The contract frontmatter itself has no `surface` field, so there is no way to know which surfaces this contract addresses without reading the journey.

### Internal Consistency: 135/150

**Invariants**: All four journey invariants are listed and consistent with the outcomes. Cascade atomicity, confirmation dialog requirement, audit records, and soft-delete are all correctly captured.

**Deductions**:
- (-10) Outcome "cancelled" does not mention audit records at all, which is correct (no deletion occurs), but the invariant section lists "Deletion from the web UI always requires a confirmation dialog before executing" — this invariant is about the process, not the outcome, and is consistent.
- (-5) Cross-references: The outcome "success" says "status_history audit records created for each deleted item" — this implies multiple records (one per sub-item + one for main item). The invariant says "Every successful deletion creates a status_history audit record" (singular). Minor inconsistency in plural vs singular.

3. **Scope "session-expired" precondition**: Narrow the precondition to specify the user was viewing an item detail page in the deletion journey context, not just "previously authenticated."

### Recommended Improvements

4. **Add surface field to frontmatter**: Add `surface: "web"` to the YAML frontmatter.

5. **Add per-outcome surface tags**: Tag each outcome with its surface (all are `web` for this step).

6. **Include all journey invariants**: List all 5 journey invariants, not just 2.

7. **Consider adding "not-found" outcome**: If a member user navigates to a non-existent item, the web UI should show a not-found page.

8. **Remove "no deletion is attempted" from validation-error**: Step 3 is about visibility, not deletion. The validation-error should focus on page rendering, not preventing deletion.
