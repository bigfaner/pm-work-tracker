## Detailed Dimension Analysis

### 1. Completeness (Score: 126/200, Threshold: 120 -- PASS)

**Strengths:**
- All 5 happy-path journey steps have corresponding contracts.
- Each contract includes well-formed outcomes with Preconditions, Input, Output, State, and Side-effect fields.
- Metadata (frontmatter) is correct across all contracts: journey name, step number, step-action, generated date, sources.
- Journey invariants are reproduced in each contract.

**Deficiencies (critical):**
- **Edge cases are completely missing as contracts.** The journey defines 9 edge cases (E1 through E9). None have dedicated contract files. This is the single largest gap:
  - E1 (invalid date format) -- no contract, though step-2 partially covers it as an outcome
  - E1b (start after end time) -- no contract, though step-2 partially covers it as an outcome
  - E2 (single sub-item) -- no contract
  - E3 (identical creation times) -- no contract
  - E4 (session expired during edit) -- no contract, though step-2 has a session-expired outcome
  - E5 (unauthorized API access) -- no contract, though step-5 has an unauthorized outcome
  - E6 (unauthenticated API request) -- no contract
  - E7 (malformed API request) -- no contract, though step-5 has a validation-error outcome
  - E8 (non-existent main item) -- no contract
  - E9 (concurrently deleted sub-item) -- no contract

- **No standalone fact table.** Contracts do not include a fact table section that maps journey facts to contract claims. The journey references facts with `<!-- fact: ... -->` annotations but contracts do not reproduce these.

**Deduction rationale:** Edge cases represent 9 of 14 total journey scenarios (64%). Their absence is a severe completeness gap. The happy-path coverage is solid, but edge-case coverage is near-zero for standalone contracts.

### 2. Semantic Purity (Score: 172/200, Threshold: 120 -- PASS)

**Strengths:**
- Language is natural and domain-oriented throughout.
- Inputs and outputs are described in user/behavioral terms, not implementation terms.
- No coupling to specific UI frameworks, database schemas, or HTTP libraries.

**Minor issues:**
- Step-2 `State` field says "Sub-item plan_start_date updated in database" -- this references a specific database column name (`plan_start_date`), which is implementation coupling. Should say "Sub-item start time is persisted" or similar.
- Step-5 references `HTTP 403`, `HTTP 400`, `ERR_FORBIDDEN`, `VALIDATION_ERROR` -- these are protocol-level details acceptable for an API surface contract, but the specific error code strings (`ERR_FORBIDDEN`) couple to implementation. Should use generic descriptions like "authorization error response" unless the API handbook mandates these exact codes.

**Deduction rationale:** Mostly clean. The database column name in step-2 and specific error codes in step-5 are the only violations.

### 3. Precondition Exclusivity (Score: 117/150, Threshold: 90 -- PASS)

**Strengths:**
- Preconditions are distinct from inputs -- they describe state that must hold before the user acts.
- Preconditions are generally sufficient to enable the outcome.
- Each outcome within a contract has different preconditions.

**Issues:**
- Step-3 `success` precondition: "A sub-item's start time was just edited in the previous step" -- this is a temporal/sequential precondition that creates tight coupling to step-2 execution order. It is not independently reproducible. A better precondition would describe the resulting state (e.g., "A sub-item has a start time that differs from its original value").
- Step-1 `session-expired` precondition: "The user's session has expired before opening the edit dialog" -- this is identical in structure to other session-expired preconditions but lacks the setup context (user was previously authenticated with the dialog not yet opened). Minor ambiguity.
- Step-2 `start-after-end` precondition: "A sub-item has an end time set to a specific date" -- should specify the end time exists rather than referencing "a specific date" which is vague.

**Deduction rationale:** Generally good but step-3's sequential coupling and vague preconditions in step-2 edge cases reduce the score.

### 4. Fact Alignment (Score: 97/150, Threshold: 90 -- PASS)

**Strengths:**
- Step-5 references "Fact Table ROUTE_MAIN_ITEM_LIST" in its reasoning comment, showing traceability.
- Contracts generally align with journey facts: start time edit behavior, creation-time sort, etc.

**Issues:**
- **No fact annotations in contracts.** The journey uses `<!-- fact: prd-spec #2, Story 2 AC1 -->` annotations extensively. Contracts do not reproduce any of these. There is no traceability from contract claims back to source facts.
- **Inferred outcomes lack explicit source marking.** While `<!-- source: inferred -->` and `<!-- reasoning: ... -->` comments exist, they are inconsistent. Step-1 `session-expired` is marked `<!-- source: inferred -->` with reasoning, which is good. But no contract outcome maps to the specific journey edge cases by ID (e.g., "Covers journey E4").
- **No fact table section.** Each contract should include a fact table mapping claims to sources. None do.

**Deduction rationale:** The absence of fact annotations and a fact table is significant. Inferred markings are present but incomplete and inconsistent.

### 5. Surface Fitness (Score: 132/150, Threshold: 90 -- PASS)

**Strengths:**
- Steps 1-4 are web surface contracts and correctly describe web interactions (dialog, navigation, display).
- Step 5 is an API surface contract and correctly describes API request/response patterns.
- Surface-appropriate outcomes are present: session-expired for web, unauthorized/unauthenticated/validation-error for API.
- HTTP status codes in step-5 are appropriate for API surface.

**Issues:**
- Step-5 is missing the `unauthenticated` outcome. The journey has E6 (unauthenticated API request) but step-5 only covers `unauthorized` (authenticated but lacking permission). These are distinct outcomes and both should be present for API surface fitness.
- Step-5 is also missing a `not-found` outcome. Journey E8 describes a non-existent main item scenario. API surface contracts should cover this common boundary.
- Web contracts (steps 1-4) are missing the `concurrently-deleted` outcome. Journey E9 covers this scenario for web surface.

**Deduction rationale:** Surface tags match journey surfaces correctly, but missing API outcomes (unauthenticated, not-found) and missing web outcomes (concurrently-deleted) reduce fitness.

### 6. Internal Consistency (Score: 133/150, Threshold: 90 -- PASS)

**Strengths:**
- Journey invariants are consistently reproduced across contracts.
- Cross-references between steps are logical (step-2 edits, step-3 verifies, step-4 observes).
- State transitions are consistent: step-2 is the only mutating contract; others are read-only.
- No contradictions found between contracts.

**Issues:**
- Step-3 references step-2 in its precondition ("just edited in the previous step") but does not use a formal cross-reference mechanism (e.g., `<!-- ref: step-2/outcome:success -->`).
- Invariant "Sub-item lists on main item detail pages are always sorted by creation time in descending order" appears in steps 1, 4, 5 but not in step-2 or step-3. Step-3 does have "Editing start time does not affect the sub-item's position in the sorted list" which is a corollary but the invariant is inconsistently applied.
- Step-1 invariant includes "The sub-item edit dialog always includes a start time field" which is a UI concern, while step-5 includes "Sub-item creation time determines sort order" which is a data concern. These are correct but the invariant sets are not uniform across all contracts.

**Deduction rationale:** Good consistency overall. Minor issues with cross-reference formality and invariant uniformity.
