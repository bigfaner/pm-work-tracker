## Revision Guidance (Priority Order)

### 1. [Critical] Step 2 "unauthorized-api" outcome is mislabeled and inconsistent (impacts Completeness, Internal Consistency, Fact Alignment)

The outcome named "unauthorized-api" actually describes a *successful* API access scenario. This is the single largest quality issue.

**Fix**: Either:
- (a) Rename to "success-api" or "authenticated-api-access" and keep the success content, OR
- (b) Change the content to describe an actual unauthorized scenario (member with nil role_key hitting a restricted endpoint and getting 403), which would add missing coverage.

Recommendation: option (b) -- rename to "forbidden-endpoint" and describe the member user with nil role_key attempting to access a restricted API endpoint (e.g., delete), receiving a 403. This covers the real unauthorized case for nil-roleKey users and is currently missing from Step 2.

### 2. [High] Add missing outcomes to Step 2 (impacts Completeness)

Step 2 covers the same web login surface as Step 1 but lacks the `validation-error` and `session-expired` outcomes that Step 1 includes. Since the web login surface is identical, these outcomes should be present.

**Fix**: Add `validation-error` and `session-expired` outcomes to step-2 contract, mirroring Step 1's structure.

### 3. [High] Resolve main_item:list vs main_item:read inconsistency in Step 4 (impacts Fact Alignment, Internal Consistency)

Step 4 "unauthorized-api" references `main_item:read` but the journey Setup defines the member permission as `main_item:list`. These must be reconciled.

**Fix**: Verify which permission name is correct from the PRD/design, then use the correct term consistently. If they refer to the same thing, standardize on one name.

### 4. [Medium] Remove implementation coupling from outcome descriptions (impacts Semantic Purity)

Several outcomes reference HTTP status codes (403, 404, 400), error code constants (ERR_FORBIDDEN, ITEM_NOT_FOUND, VALIDATION_ERROR), and middleware internals.

**Fix**: Replace with behavior-level descriptions:
- "HTTP 403 with error code ERR_FORBIDDEN" -> "an authorization error response"
- "HTTP 404 with error code ITEM_NOT_FOUND" -> "a not-found error response"
- "the middleware falls back to querying the member role's default permission set" -> "the system provides the member role's default permissions"

### 5. [Medium] Clean up preconditions that conflate actions with state (impacts Precondition Exclusivity)

Several preconditions describe actions the user is taking rather than the state of the world before the action.

**Fix**: Restructure affected preconditions:
- Step 2 "unauthorized-api": "A member user with nil role_key attempts an authenticated API request" -> "A member user with nil role_key is authenticated; the user has a valid API token"
- Step 3 "pm-only-actions-hidden": "A member user is viewing an item detail page..." -> "A member user is logged in; an item detail page is accessible"
- Step 4 "unauthorized-api": "A member user without main_item:read permission attempts to access the list API" -> "A member user is authenticated without the required list permission"

### 6. [Medium] Remove circular assertion from Step 5 precondition (impacts Internal Consistency, Precondition Exclusivity)

Step 5 "success" precondition: "the middleware correctly falls back to member preset permissions" assumes the fix works as a precondition.

**Fix**: Change to: "A member user with nil role_key is authenticated" (the rest is what the outcome verifies).

### 7. [Low] Add explicit fact annotations to journey invariants (impacts Fact Alignment)

The Journey Invariants section at the bottom of each contract lacks explicit fact source annotations.

**Fix**: Add `<!-- fact: prd-spec #6 -->` or `<!-- source: journey-invariant -->` annotations to each invariant.
