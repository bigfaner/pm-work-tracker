### Critical Issues Requiring Revision

#### 1. Missing Fact Tables (All Contracts)

No contract contains a formal fact table section. Each contract must include a structured fact table that maps claims to source evidence. Format:

```
## Fact Table
| Claim | Source | Status |
|-------|--------|--------|
| sub_item:update auth required | api-handbook.md Move Sub Item Auth | verified |
| 400 for closed target | api-handbook.md Error Responses row 1 | verified |
| ... | ... | ... |
```

#### 2. Missing Surface Annotations (All Contracts)

Add surface tags to frontmatter and per-outcome annotations:

```yaml
---
surface_types: ["web", "api"]
---
```

And per outcome:
```markdown
## Outcome "success"
<!-- surface: web -->
```

#### 3. Missing Concurrent Move Edge Case E3 (Step 2)

Journey Step E3 describes concurrent move of the same sub-item. This is the highest-risk edge case and is completely absent from all contracts. Step 2 must include an outcome like:

```
## Outcome "concurrent-move-conflict"
<!-- source: inferred -->
<!-- reasoning: Journey E3 -- second transaction detects parent change -->
- Preconditions: "Another transaction has already moved this sub-item to a different parent"
- Input: "A second move request arrives for the same sub-item after the first transaction committed"
- Output: "The API returns HTTP 409 Conflict indicating the sub-item's parent has changed; no data corruption"
- State: "No state change; sub-item remains at first transaction's target"
- Side-effect: "none"
```

#### 4. Misplaced Outcomes in Step 3

Step 3 (verification/navigation) should only contain read-related outcomes. The following outcomes belong in Step 2:
- `source-deleted-during-move` -- describes a move-time failure
- `non-existent-sub-item-api` -- describes a move API error
- `non-existent-target-api` -- describes a move API error
- `validation-error` -- describes a move API validation error

Step 3 should instead cover:
- `success` (navigation to new location)
- `session-expired` (Web surface mandatory outcome)
- Possibly: moved sub-item no longer visible if another user moves it again during navigation

#### 5. Step 1 Missing Invariants

Step 1 declares only 2 of 5 journey invariants. All contracts must declare ALL journey invariants, or explicitly note which subset they enforce with rationale.

#### 6. Implementation Coupling in Step 2 State Field

Change from:
```
State: "Sub-item main_item_key updated to target BizKey; item_code regenerated via atomic increment; completion recalculated for both source and target main items"
```
To:
```
State: "Sub-item is reassigned to the target main item with a new code number; completion percentages updated for both source and target main items"
```

#### 7. Phantom Fact Table References

Contracts reference "Fact Table MOVE_TERMINAL_CHECK", "Fact Table MOVE_SAME_PARENT_CHECK", "Fact Table ROUTE_SUB_ITEM_MOVE" -- these named entities do not exist in any source document. Either create these fact tables or change reasoning to reference actual source locations (e.g., "api-handbook.md Move Sub Item Error Responses").

#### 8. Step 1 Endpoint in Input Field

The unauthorized outcome input references `PUT /api/v1/teams/:teamId/sub-items/:subId/move` -- this is implementation detail leaking into the contract. Change to: "An unauthorized move API request referencing the sub-item"
