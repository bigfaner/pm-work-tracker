# Business Rules: System UX Optimization Batch

## Terminal Status & Sorting

### BIZ-001: Terminal Status Definition for Main Items

**Rule**: Main items with `item_status` = `completed` or `closed` are terminal. Terminal items sort to the bottom in list views, can be filtered in progress/gantt views, and are hidden in weekly view when inactive.
**Context**: Terminal status determines sorting, filtering, and visibility across multiple views (item list, progress page, gantt chart, weekly view). A unified definition prevents inconsistency.
**Scope**: [CROSS]
**Source**: PRD "Functional Specs - 终态定义", Tech Design Interface 6

### BIZ-002: Terminal Items Sort to Bottom

**Rule**: In item list and progress views, terminal main items are sorted after all non-terminal items, preserving relative order within each group.
**Context**: Reduces visual noise by deprioritizing inactive items. Applies to both list and gantt views.
**Scope**: [CROSS]
**Source**: PRD #11, #12, Tech Design Interface 6

## Deletion

### BIZ-003: Cascade Soft-Delete in Single Transaction

**Rule**: Deleting a main item soft-deletes all its sub-items within a single database transaction. Both main item and sub-items set `deleted_flag=1` and `deleted_time=now()`. The `item_status` field is NOT modified.
**Context**: Ensures data consistency -- partial deletion would leave orphaned sub-items. Uses existing soft-delete pattern (SD-003).
**Scope**: [CROSS]
**Source**: PRD #3, Tech Design Interface 1

### BIZ-004: Deletion Records Audit Entry in status_histories

**Rule**: When an item is soft-deleted, a row is inserted into `status_histories` with `from_status=<current_status>` and `to_status="deleted"`. This is an audit record only -- `item_status` on the item itself is not changed.
**Context**: Provides audit trail for deleted items without conflicting with the soft-delete pattern (which relies on `deleted_flag`, not status changes).
**Scope**: [CROSS]
**Source**: Tech Design Interface 1, Interface 2

### BIZ-005: Delete Requires Permission Code

**Rule**: Delete operations require `main_item:delete` (for main items) or `sub_item:delete` (for sub items) permission codes. Frontend hides delete buttons via `PermissionGuard` as defensive UI; backend enforces via `RequirePermission` middleware.
**Context**: New permission codes extend the existing RBAC system. Follows existing permission-guard pattern.
**Scope**: [CROSS]
**Source**: PRD #3, Tech Design Security Considerations

## Sub-Item Move

### BIZ-006: Move Preserves Status and Assignee

**Rule**: When a sub-item is moved to a different main item, its `item_status` and `assignee_key` remain unchanged. Only `main_item_key` and `item_code` are updated.
**Context**: Move is a re-organization operation, not a status change. Preserving fields avoids unintended side effects.
**Scope**: [CROSS]
**Source**: PRD #9, Tech Design Interface 3

### BIZ-007: Move Target Validation

**Rule**: Sub-item move targets must satisfy: (1) target main item is not terminal (status not completed/closed), (2) target is not the same main item the sub-item currently belongs to, (3) target belongs to the same team. Violations return BAD_REQUEST.
**Context**: Prevents invalid moves that would break item hierarchy or bypass team isolation.
**Scope**: [CROSS]
**Source**: PRD #9, Tech Design Interface 3

### BIZ-008: Move Uses Atomic Counter for New Code

**Rule**: The moved sub-item receives a new code generated by atomically incrementing the target main item's `sub_item_seq` counter within the move transaction. Follows existing code generation pattern (BIZ-code-004).
**Context**: Reuses the proven atomic counter pattern from item creation. Guarantees unique codes under concurrency.
**Scope**: [CROSS]
**Source**: Tech Design Interface 3, conventions/item-codes.md BIZ-code-004

### BIZ-009: Move Recalculates Completion for Source and Target

**Rule**: After a sub-item move, both the source and target main items have their `completion_pct` recalculated synchronously within the same transaction.
**Context**: Maintains data integrity of the weighted average completion calculation (DM-008).
**Scope**: [CROSS]
**Source**: Tech Design Interface 3

## Filter Penetration

### BIZ-010: Filter Penetration Shows Indirect Matches

**Rule**: When filtering by assignee, results include both: (a) main items directly assigned to the filtered assignee (matchType=direct), and (b) main items whose sub-items are assigned to the filtered assignee (matchType=indirect). When status filter is also applied, both the main item status and sub-item status must match.
**Context**: Users need to find items related to a person even if the person is only assigned to sub-items, not the main item itself.
**Scope**: [CROSS]
**Source**: PRD #10, Tech Design Interface 4

## Authorization

### BIZ-011: Team Selector Filters by Membership

**Rule**: The team list endpoint returns only teams where the requesting user is a member (via `pmw_team_members` join). SuperAdmin bypasses this and sees all teams.
**Context**: Prevents users from seeing teams they don't belong to. Follows existing SuperAdmin bypass rule.
**Scope**: [CROSS]
**Source**: PRD #15, Tech Design Interface 9

### BIZ-012: Member Role Nil RoleKey Fallback

**Rule**: When `pmw_team_members.role_key` is NULL, the permission middleware queries the preset "member" role's default permission set instead of returning an empty set.
**Context**: Fixes a bug where member-role users with no explicit role_key assignment got zero permissions. The fallback ensures new members always have baseline access.
**Scope**: [CROSS]
**Source**: PRD #8, Tech Design Interface 10

## Weekly View Filtering

### BIZ-013: Weekly View Hides Inactive Terminal Items

**Rule**: In weekly progress view, terminal main items are hidden if they have no active sub-items in both the current week and previous week. "Active" means: (a) status_history change exists in the time range, (b) sub-item create_time or db_update_time falls in range, or (c) main item db_update_time falls in range.
**Context**: Reduces clutter in weekly view by hiding items that have had no recent activity.
**Scope**: [LOCAL]
**Source**: PRD #16, Tech Design Interface 8

## Empty State

### BIZ-014: Filter Empty State with Reset Action

**Rule**: When filter conditions produce zero results, display "没有符合条件的事项" with a "清除过滤条件" button that resets all filters. Applies to item list (card/table views), progress page, and weekly page.
**Context**: Extends the existing empty state convention (frontend-ux.md) with filter-specific behavior.
**Scope**: [CROSS]
**Source**: PRD "Empty State Handling"

## Delete Confirmation

### BIZ-015: Delete Confirmation Dialog

**Rule**: All delete operations require a confirmation dialog. For main item deletion, the dialog shows "将同时删除 N 个子事项". Confirmation is the only trigger for the delete API call.
**Context**: Prevents accidental data loss. Required by security requirements.
**Scope**: [LOCAL]
**Source**: PRD #3
